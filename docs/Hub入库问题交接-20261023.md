## 1. 心跳已到 MQTT，但 Hub 最后心跳不更新

原实现 `IoTStateService.accept` 和 `IoTConfigGetHandler` 不接受任何未来时间。曾抓到 PLC 时间只快约 0.03～0.85 秒，STATE 队列为空、工作线程空闲，Hub 仍不更新会话/最后心跳，配置预览报 `PATCH_CAPABILITY_UNAVAILABLE`。这是时间边界问题，不应混同数据库排队。

PLC 现在持续跟随与 Hub 同机的时间源，但秒级 RTC、网络延迟和正常偏差仍客观存在。建议 Hub 使用统一的控制消息新鲜度策略，评估小幅正向容差。实验值为 5 秒：它不是最终产品要求，仍需 Hub 项目确定。必须同时验证同会话重放不能续命、旧会话不能恢复、较快旧 boot 的时间不能阻止新 boot 接管，不能仅放宽一个时间判断。

## 2. 网关行锁使心跳、配置和遥测相互等待

原 `IoTStateMapper` 为心跳锁网关 `FOR UPDATE`，随后对每个设备分别执行状态 UPSERT。50 台就有 50 次串行远程 JDBC 往返，整个期间持有网关锁。原 `IoTReleaseMapper` 在遥测入库路径也锁同一行 `FOR UPDATE`，遥测与心跳、发布因此互斥。

实验把设备状态改成单次 `jsonb_to_recordset` 批量 UPSERT；状态使用 `FOR NO KEY UPDATE`，遥测读取保护使用 `FOR KEY SHARE`。发布、解绑和保留清理仍需保留适当排他边界。调整锁模式前必须核查全部调用者，保证配置切换、清理和入库不能越过版本边界；收据去重和“事务提交后才 STORED”也必须保留。

## 3. 只读配置接口在锁内编译完整点表，代价随点数增长

调用链：`DefaultIoTGatewayService.getBinding` → `view` → `draftDirty` → `IoTSnapshotCompiler.preview`。网关读取持有排他行锁，旧编译器按设备读取 Device、按设备读取点表，再按点读取 Variable。50×5 时，仅这部分就约 **50 + 50 + 250 = 350 次远程查询**。

在前述部分实验已运行后，仍观察到网关锁等待约 29.245 秒、一次遥测处理约 30.333 秒、STATE 执行约 4.829 秒；v10 发布到 APPLIED 的脚本测量为 39.844 秒，后续一次 API 读取超过 30 秒超时。说明只改心跳 UPSERT 不足以消除卡顿。具体数值属于该远程开发数据库环境的样本，不是所有部署的基准。

建议优先减少快照编译查询次数，再评估普通读取是否确实需要排他锁；如改成锁外计算，必须验证草稿修订和一致性。工作区已有批量加载 Device、PointConfig、Variable 的实验，但**未部署且整组回归未通过**。不要把实验补丁直接当作发布版本。

## 4. Hub 与远程数据库混用时钟

本轮数据库时钟曾比 Hub 主机快约 35 秒。`IoTMessagingMapper.dueParents` / `nextCommand` 用数据库 `now()` 过滤最后心跳，而在线状态及部分业务判断使用 Hub 时钟，同一心跳可能得到不同的新鲜度结论。

建议在线判断统一使用 Hub 的时间基准并通过参数传入 SQL，或者统一全部系统时间源；由数据库生成的重试期限仍应按其原始语义处理。工作区有传入 Hub 时间截止值的实验，尚未部署。不要用固定减去 35 秒修复，也不要用数据库 `now()-last_heartbeat_at` 冒充 Hub 实际收到心跳的年龄。

## 5. 后续建议的验证顺序

1. 在 Hub 项目先明确并整理当前工作区与正在运行的实验 JAR，避免测试到旧代码。
2. 分别记录 MQTT 接收时间、队列等待、事务/锁等待、真实 STORED 回执时间及状态投影时间；以 sourceMessageId 串联，不以 HMI 显示代替入库证据。
3. 50×5 正常采集时反复读取配置详情、预览并发布，验证查询/锁等待收敛；检查单网关 DATA 调度并发是否仍限制吞吐，不能只增加全局线程数。
4. 回归同消息重试去重、并发发布/删除/解绑、版本冲突、旧会话/重放、新 boot、微小正时差和数据库时差。
5. 稳定后再开展持续压力测试。当前不宣称 Hub 稳定性或 8 小时长测通过。
