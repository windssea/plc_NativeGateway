## M14审计什么

M14是三方联调的原始事实取证接口，目的是核对采样与上报规则是否一致。它不修改系统时间，不是安全操作日志，也不是P06性能认证。

| 要回答的问题 | 原始事实及核验边界 |
|---|---|
| 是否发生漏轮询或漏报告槽 | 保留名义采样槽、完成单调时刻、首次激活原点及跳槽计数；外部核验器独立重算已完成前缀。未完成请求和静默尾界不能据此宣称无缺口 |
| 采集时有时间，决策时是否已经失效或换代 | 同时保留采集时钟版本、决策时刻/版本及当前有效性，不把采集时有效当成稍后入队必然合法 |
| 某条事件为什么没有上报 | 结合原有终态/原因，区分正常策略过滤、TIME_INVALID、容量拒绝等；未知不补成正常，也不因时间失效停止合法历史ACK处理 |
| 已接纳事件进入哪个批次，最终去了哪里 | 原有M12/M13捕获身份与批次关联连接到messageId/原始值序号/hash；真实Hub收据/入库及本地释放须由外部工具另行核验 |

M14本身只保存原始事实并检查版本、类型、稳定性及编码，不替代独立选择器，也不自行认证Hub入库或本地释放。其审计ACK仅确认已落盘的审计副本，和业务STORED ACK不同。

例如：采集发生在有效时钟下，但处理积压期间时钟失效。按共同规则，这条数据可能应为TIME_INVALID；只有采集UTC的旧日志无法解释该结果。v2的决策时钟事实可让独立工具判断PLC和Python是否采用同一规则。反之，若本机导出器丢失审计副本，也不能仅凭审计失败断言业务DATA丢失。
