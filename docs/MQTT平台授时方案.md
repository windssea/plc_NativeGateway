# Hub、原生 PLC、Python IoT 的 MQTT 平台授时共同方案

状态：2026-10-23 设计草案，尚未实现、编译、下载或联调。已补充三方时间处理，并复核运行启动顺序、时间失效门槛、历史补传、迟到确认和跨重启时间基准的冲突。本轮只完善本文档，不修改任何项目代码或改变正在运行的 PLC、Python IoT Agent、Hub、broker、NTP 或点表。Hub 工作区已有其他任务的改动，实施前应先确认现状，不能回退此前实验补丁覆盖新工作。

## 目标和边界

现场已有 Hub 与 MQTT broker 时，原生 PLC 与 Python IoT Agent 均复用各自现有 MQTT 连接取得 Hub 时间，无需额外运行 NTP。原生 PLC 继续使用 IEC/ST 和 Web HMI，Python IoT 继续使用现有采集执行器及本地初始化/诊断页面；配置、遥测及业务回执保持现有 IoT 结构。授时是所有 Agent 均可选择实现的公共扩展，不增加 NativeGateway 或 Python 专用的 Hub 分支。

首版同步的是 **Agent 采样及网关报文使用的逻辑 UTC 时钟**，不直接写 PLC 操作系统 RTC，也不修改 Python 宿主机/容器系统时钟：系统日志、WBM 的系统时间以及其他应用不会随之校准。逻辑时钟以单调计时推进，独立于系统墙钟的人工修改或 NTP 跳时；运行平台的休眠、暂停及单调计时连续性仍需单独验证。是否进一步校准操作系统应另行核实原生服务能力和权限。Hub 作为现场统一时间基准，自己未对外校准时仍不能保证真实北京时间准确。

MQTT 连接建立之前无法通过该连接授时。如现场使用 TLS，控制器首次连接前仍需有足以验证证书的系统日期；不能通过关闭证书校验解决。当前 1883 联调不涉及这个握手前置问题。

| 参与方 | 负责内容 | 本地存储差异 |
|---|---|---|
| Hub | 唯一现场时间权威、公共契约及授时响应、业务接入与重放边界 | 持久会话/版本/收据与最新值排序不能因授时绕过 |
| 原生 PLC | 实现共同授时状态机、IEC/ST 逻辑时钟、采样时间有效性及 HMI 诊断 | 当前遥测 outbox 为 RAM，整机重启不保留未确认批次 |
| Python IoT | 实现同一授时状态机和逻辑时钟，接入 Modbus/OPC UA、报文与本地诊断 | SQLite Outbox 跨进程/系统重启保存原批次，必须另行处理年龄及重试计时 |

本文公共时间规则适用于两种 Agent；`NowMs`、`NG_TimeSync`、ULINT 和 Web HMI 等属于原生 PLC 实现，Python 使用对应的单调时钟、时间服务和本地诊断。协议可选表示旧 Agent 不必立即升级；旧 Agent 仍需自行保证系统时间正确，不代表新版 Hub 放弃时间校验。

正文 `TimeValid`、首次同步及发送门槛均指“平台授时”模式。“控制器/宿主机系统时间”是显式选择的兼容模式，按原有业务路径运行并单独显示时间未获平台验证，不得因 MQTT 连通就显示已同步，相关 Outbox 入队时间标记为未验证。新部署推荐平台模式，已有安装升级时须保留并明确展示所选模式，不静默切换。切换时间源要暂停新业务发送、撤销未完成授时请求并重新检查时间边界和缓存；不能借切换绕过大幅回拨限制，不能改写原批次或自动提升旧入队时间的可信度。

## 当前实现依据

- `src/Main.st` 的 `NowMs` 已用于采集、重试、心跳和组批调度；`UnixMs` 每周期由 `NG_Unix(RTC, Bootstrap.UtcOffsetMinutes)` 计算，当前 RTC 只有秒分辨率。
- `NG_Modbus` 把 `UnixMs` 写入采样时间；`Main` 的公共 Header 及状态、配置请求、回执、诊断使用相同时间源。
- `src/NG_Mqtt.st` 当前依次订阅 `config/set`、`config/patch`、`data/ack`。没有授时请求、响应或时钟状态机。
- 现有 IoT 契约没有 `time/request`、`time/response`，多个已有消息禁止未知字段；不能随意给原心跳、config/get 塞入时间字段。
- Hub 有独立 Topic 白名单、MessageKind、Schema 和语义检查，需要一同扩展。首次授时不能经过已有“必须存在有效心跳会话、设备时间必须新鲜”的业务门槛。
- Python `PLCnext-iot/src/plcnext_iot/devices/modbus.py`、`devices/opcua.py` 的样本，`messaging/health.py` 的心跳，`messaging/messages.py` 的公共 Header 以及 `reporting/service.py` 的新批次 Header 仍使用 `time.time_ns()`。采集调度、报告周期、样本陈旧判断和 uptime 已使用 `loop.time()`/`time.monotonic()`；首版应复用这些单调计时边界，不做全局替换。
- Python `storage/outbox.py` 保存 `created`、`attempts`、`next_due`，当前由调用方传入 `time.time()`：`created` 用于自入队起七天过期，`next_due` 用于首轮 30 秒/后续 60 秒重试；打开数据库以及 MQTT 重连发送循环会将 PENDING 的 `next_due` 清为 0。系统回拨/前跳会影响等待和过期判断，这些现状尚不满足本文目标规则。
- Python `storage/database.py` 当前对 `telemetry.db` 执行格式版本 1、gateway 身份及完整性检查，使用 SQLite WAL、synchronous=FULL 和单独 StoreWorker；修改 Outbox 元数据必须有显式迁移，不能仅增加字段而仍沿用原格式检查。旧库 `created` 没有时间可信度证明，不能因升级后授时成功就追认为可信。

## 三方运行启动与恢复顺序

本节描述运行期依赖，不同于后文代码实施/发布顺序。Hub 沿用既有部署入口与基础服务健康顺序；broker 和 Hub 不得等待首个 Agent 心跳或 APPLIED 才开放授时。两种 Agent 允许先于 Hub 启动，Hub 未就绪时仅进行有界重试及本地采集，不要求人工调整全站开机顺序。

| 阶段 | 可以执行的动作 | 不得等待或误认的条件 |
|---|---|---|
| 本地恢复 | 检查 Bootstrap/身份、配置及 Outbox；建立进程上下文，恢复可用本地采集 | 不把旧 UTC 当现在；读库失败不能伪装为空配置或版本 0 |
| MQTT 就绪 | 使用当前 boot/session 连接并等全部必要 SUBACK，包括授时、配置及业务 ACK；接收分流开始工作 | 订阅完成仅表示传输就绪，不表示已授时、在线或 APPLIED |
| 时间就绪 | 在无心跳/配置前发送 time/request，按预算取得可信锚点 | 不能等待新配置、新 GOOD 样本或第一条 STORED 才授时 |
| 控制恢复 | 时间有效后优先提交本 session 的正常心跳，再发 config/get；处理配置与实际应用结果 | 明确无已提交配置时，可发 activeConfigVersion=0、WAITING_CONFIG 的合法空设备心跳；不能编造已应用版本 |
| 数据发送 | 通过独立的新数据/历史批次资格检查后有界发送，控制与真实 ACK 持续处理 | 不能等待 Outbox 排空才发心跳/取配置；也不能等待新样本才允许旧批次恢复 |

“控制恢复完成”在客户端只表示已用当前有效时间向传输层提交正常控制报文，不代表 Hub 已处理。MQTT PUBACK 不能证明 Hub 接纳心跳或配置；当前协议没有心跳业务 ACK，不增加一个不存在的确认依赖。Hub 控制/状态处理可能跨队列乱序，Agent 应保持新心跳及重新生成的 config/get 的有界周期重试（首版仍采用正常 30 秒节奏），验收以 Hub 实际会话/配置状态确认闭环；不因暂未推进就无限快速重连。Hub 重启但 Agent MQTT 连接未断开时，同样依靠持续心跳和 config/get 重新建立进程内证据，授时服务不承担配置就绪确认。

数据发送资格分开定义：

- **新批次形成**：当前时间有效、本地配置已实际提交、样本属于当前配置和有效时间代际，并满足报告策略；不能在首轮授时前形成平台批次。**发送新批次**还须完成当前 session 的复校及正常控制恢复提交；旧锚点仍可信的新 session 恢复期间允许有界入队，不等于允许立即发送。
- **历史批次**：当前时间有效且 MQTT/正常控制发送可用，原批次身份/哈希/历史版本完整，未被明确阻止发送；不要求当前启用采集、不要求新样本为 GOOD，也不要求 Hub 期望的最新版本已 APPLIED。WAITING_CONFIG 或 DISABLED 不应单独阻塞原有持久批次补传，显式维护停发/解绑/删除等原有边界仍须服从。Hub 按真实历史版本与绑定决定接收，允许的可重试拒绝不能反过来阻塞授时或心跳。

同进程 MQTT 重连：立即作废旧 session 请求和尚未提交的旧 session 控制报文，保留仍可信锚点用于本地采样/有界入队，但新连接的业务发送先关闭，完成该 session 的复校及控制恢复后再开放；复校失败不以旧锚点偷偷跳过此门槛。Hub 重启但 MQTT 未断开时无从即时获知其系统跳时，偏差发现受复校周期限制；“约 1 秒”是稳定时间基准下的目标，不是任意 Hub 调时瞬间仍准确的承诺。正常服务重启与系统大幅调时的验收分开。

## 建议共同契约：timeSyncV1

在 `iot/v1/gateway/{gatewayId}` 下新增以下可选 Topic，两端 QoS 1、retain=false、最大负载 2048 字节。名称和字段是本方案建议，不代表现有协议已经支持。

| 后缀 | 方向 | 用途 |
|---|---|---|
| `time/request` | Agent → Hub | 原生 PLC/Python IoT 使用同一字段和单调计数发起授时，允许在首次有效心跳之前发送 |
| `time/response` | Hub → Agent | 原样关联请求并返回 Hub 接收及准备发送时的 UTC 毫秒 |

请求示例：

```json
{
  "schemaVersion": 1,
  "gatewayId": "NG-HUB-2152-01",
  "requestId": "t-ng-demo-23-1",
  "bootId": "ng-demo-23",
  "sessionId": "ng-demo-23-1",
  "clientMonoMs": 123456
}
```

响应示例，必须回显前述身份、关联 ID 和计数：

```json
{
  "schemaVersion": 1,
  "gatewayId": "NG-HUB-2152-01",
  "requestId": "t-ng-demo-23-1",
  "bootId": "ng-demo-23",
  "sessionId": "ng-demo-23-1",
  "clientMonoMs": 123456,
  "serverReceivedAt": 1792739100120,
  "serverSentAt": 1792739100125
}
```

所有时间单位为毫秒；服务端字段为 Unix UTC 毫秒，不能减时区偏移。计数和 ID 应明确范围：建议沿用现有 ID 的最长 64 字符限制，整数限制在跨语言可精确表达的范围。请求故意没有依赖 RTC 的 `timestamp`；不能复用一个强制要求设备绝对时间的通用 Header。

`requestId` 使用当前进程/启动身份和独立授时请求序号生成；原生 PLC 复用持久启动计数形成的身份，Python 复用当前 `ProcessBootContext` 的随机 bootId，均不依赖 RTC，也不占用遥测 sequence。sessionId 必须属于当前 MQTT 连接。Python 同进程设置重载保留进程 bootId，新进程生成新 bootId；磁盘旧批次仍携带原 bootId，不能拿它建立新授时会话。每次重试生成新 requestId，旧请求作废，同一响应只接受一次。QoS 重复投递、其他网关、旧 boot、旧 session、未知或已完成请求、retained 响应全部不能再次改变时间。

非 retained 是发布约束，接收端仍须拒绝可识别的 retained 投递；不能只凭接收 RETAIN 标志判断发布者身份或消息新鲜度。主防线始终是授权响应 Topic、当前请求/boot/session 的精确关联、单次接纳及单调截止点。响应即使在接收回调中及时到达，处理时也须确认请求尚未超时作废且仍属当前连接；过期队列中的响应不能在恢复事件循环后重新激活旧锚点。

契约、示例和结构/语义测试应作为共享公共扩展在三方同步，保留旧消息定义。Hub 先支持新 Topic，旧 Python Agent 不发送请求时保持既有行为；不要要求旧 Agent 为兼容新版 Hub 同时实现授时。现有共享契约哈希测试与原生侧解析约束需要协调，不能各自维护不同字段。

## 时间估算与校准

Agent 在真正提交本次 MQTT 发布时记录 `m1`，在拿到响应时立即记录 `m4`，均来自同一进程/boot 的同一单调计时源：原生 PLC 使用 `NowMs`，Python 使用统一的 `monotonic_ns()` 整数毫秒映射。`clientMonoMs` 必须等于本次保存的 `m1`；不能把排队创建请求的时间当成发送时间，也不能在耗时 JSON 解析完成后才记录接收时间。Hub 在入口记录 `t2`，临近实际 MQTT 发布调用时记录 `t3`，分别写入 `serverReceivedAt`、`serverSentAt`。两端都不能把 QoS 1 的 PUBACK 到达时间当作发送起点。

建议估算：`rtt=m4-m1`，`serverProcessing=t3-t2`，`pathDelay=rtt-serverProcessing`，响应到达时逻辑 UTC 约为 `t3+pathDelay/2`。之后以该 UTC 与 `m4` 为锚点，用单调时间推进。Hub 入队等待若位于 t2 与 t3 之间可以扣除；t3 之后的传输排队仍会影响估算，因此仍须限制总 RTT。

这是借鉴 [RFC 5905 第 8 节](https://www.rfc-editor.org/rfc/rfc5905.html#section-8) 的往返测量思路，并不是通过 MQTT 实现或声称符合 NTP。路径不对称、ST 任务周期及传输队列会限制精度，不能宣称毫秒级同步。首次连接采集若干有效样本，优先选低时延样本；拒绝时间关系异常、明显负延迟、过期和过高时延响应，微小计量误差容差需在实现中明确。

以下参数作为三方首版实现与隔离联调的共同起点，修改时须同步三方契约说明及验收断言，不是当前产品承诺。正常局域网以相对 Hub 偏差不超过约 1 秒为初期目标，验收须包含观测误差，不能仅看一次应答就认定长期准确。

### Hub 计时与异步发送边界

Hub 在记录 `t2` 时同时保存单调时刻 `h2`，实际准备发布时同时记录 `t3` 和 `h3`。计算 `wallElapsed=t3-t2`、`monoElapsed=h3-h2`；任一值为负，或 `abs(wallElapsed-monoElapsed)>50 ms`，均视为本次测量期间系统时间不连续，不发布该响应，记录 `HUB_CLOCK_CHANGED`，由设备超时后重试。服务端处理时间上限 500 ms 同时约束这两个耗时。该检测不能发现两次请求之间发生的跳时，后者由两种 Agent 各自的偏差检查处理。单调时间只用于内部校验，首版不新增响应字段。

`t3` 必须在发送执行器取得执行机会、连接及发送资格检查完成后，临近实际 SDK 发布调用时取得并序列化。当前 Hub `publish` 会先复制 payload 再进入异步队列，实施时需要提供延迟构造授时响应的发送入口或等效能力；不能在业务服务中提前生成 `t3` 后排队，还将此队列耗时视为已准确扣除。`t2` 之前以及实际发布之后的传输和 broker 排队仍计入路径延迟，最终受 Agent 的总 RTT 门槛约束。独立有界处理须覆盖接收和发送两端，不能只给路由新增线程。

两种 Agent 均先检查 `m4>=m1`、`t3>=t2`，再以有符号差值计算延迟，原生侧须避免 ULINT 下溢。首版允许 `pathDelay` 最低为 -50 ms，以容纳计量粒度；处于 [-50, 0) ms 时按 0 估算并保守计入误差，低于 -50 ms 则拒绝。原生 PLC 单调计时的长周期边界、任务延迟和计数范围，以及 Python 网络线程/事件循环排队和系统休眠边界均须验证，不能只证明 RTC 不影响计时。

### 首次同步、超时与平滑修正

| 参数 | 首版暂定规则 |
|---|---|
| 单次请求 | 同时仅一个待处理请求；从 `m1` 起 2000 ms 超时，超时即作废 requestId；Hub 处理上限 500 ms |
| 首轮预算 | 从进入本轮授时阶段开始最多 30 秒、最多 10 次尝试，先到者结束；包括发送等待、请求超时和重试间隔，单调计时，不因收到无效响应重置 |
| 首选样本 | 争取取得 3 个有效样本，按各自 `m4` 推进到同一单调时刻后，估算 UTC 的最大差不超过 500 ms，选择路径延迟最低的样本 |
| 单样本启动 | 预算结束时不足 3 个样本，允许用一个 RTT 不超过 500 ms 的有效样本启动；已有其他有效样本时仍须满足上述一致性检查，存在冲突不能挑选单样本绕过；标记“单样本初始同步”并在 10 秒后复校 |
| 首轮失败 | 无符合启动条件的样本或样本相互冲突时，保持 `TimeValid=false`；轮间按 5、10、20、40、60 秒退避，附加 0～20% 错峰后硬限 60 秒；本地采集继续 |
| 正常复校 | 每 300 秒，附加 ±10% 错峰；重连立即进入有界复校，不能沿用旧 session 的未完成请求 |
| 小偏差 | 在同一单调时刻比较目标 UTC 与当前逻辑 UTC，绝对偏差不超过 1000 ms；逻辑时钟按正常速率的 99.5%～100.5% 平滑推进，禁止直接向后跳或通过长期冻结时间修正；含修正残差的总误差预算达到 1 秒时仍须暂停业务，不能仅因属于小偏差就忽略预算 |
| 大偏差 | 绝对偏差超过 1000 ms，立即暂停新业务发送及新批次形成并进入重同步，旧批次发送也暂停；重新完成有界采样确认，不能以单次异常响应立即换锚点或判定需要维护 |

每个候选样本保留自己的 UTC/`m4` 锚点；最终选定时必须补上从该 `m4` 到当前时刻的单调增量，不能在三次测量后直接使用第一条响应到达时的旧 UTC。初始误差预算至少覆盖半路径延迟、两端计时粒度、Agent 接收和任务延迟；即使 RTT 通过，也不能在预算超过 1 秒时标记为有效同步。当前 2000 ms RTT 上限只是响应筛选上限，不等于每个通过该门槛的样本都满足 1 秒目标。

复校仅因无响应/高延迟失败时，不立即抹除同一 boot 内仍在误差预算内的锚点，而是进入离线保持；再次连上 MQTT 也不自动刷新“上次同步成功”。已经因可疑大偏差或连续性异常关闭的时间门槛，不得在随后测量超时后无提示退回旧锚点；须取得新的合格测量并通过时间边界检查才恢复。首次同步失败与旧 Hub 未响应在首版只能诊断为授时超时，不能仅凭超时断言对端不支持协议。

### 大幅回拨与首版恢复限制

同一逻辑时间代际内，已对外使用的 UTC 不倒退。普通重启/重连且 Hub 时间连续时，必须完成自动授时及业务恢复。大偏差确认后，只有目标时间已晚于本机此前对外使用的最大 UTC，且没有已知 Hub 旧时间排序障碍，才允许建立新锚点；仍须完成正常控制恢复提交及各自数据资格检查，历史批次不等待新样本。冷启动没有本机旧锚点，不代表 Hub 中没有该网关的历史时间边界。

**首版不承诺任一种 Agent 已上报后大幅回拨的自动恢复。** 例如 Hub 从 15:00 调回 14:00，即使 Agent 建立新 MQTT session，Hub 持久化会话的旧时间仍可能阻止新会话接管；现有进程启动时间和最新值排序也可能形成边界。不能以“重连即可恢复”作为实现前提，不能伪造 boot、更换 gatewayId、直接删会话/历史值或全面放宽业务新鲜度校验。

确认回拨且当前目标仍低于此前时间边界时，两种 Agent 均保持本地采集，暂停新 UTC 业务，在原生 HMI/Python 本地诊断显示“平台时间回拨，需要维护”，保留旧锚点、最近确认的偏差和待处理队列诊断；不得把其显示为已恢复。计划大幅调整 Hub 时间应进入维护窗口。首版维护恢复仅接受将 Hub 时间纠正到正确现场基准、并已越过既有排序边界后重新授时的路径，按需要重启 Hub 服务以重建进程时间基准，再核实新心跳、配置、新样本及真实回执。重启本身不清除持久化边界，也不能保证已能恢复；若必须保留低于历史边界的新时间，首版应明确报告不支持，等待后续受控时间代际方案，不能靠等待固定超时就宣告成功。

后续若要求回拨后自动恢复，需要另行定义由 Hub 授权的时间代际、旧/新会话隔离、最新值更新顺序及旧批次补传规则，保持重放保护；本草案不以增加一个未定义的 epoch 字段替代这些设计。验收应分别报告“正常自动恢复通过”和“超出首版范围的回拨被正确阻止”，不能将维护等待计入自动恢复成功。

时间失效时，关闭的是业务形成/发送门槛，不是 MQTT 接收循环或本地采集。进入无效状态或离散重建锚点时使本地采样有效性代际推进，正常小偏差平滑复校不反复清空报告缓存；准备中批次、StoreWorker 队列任务及尚未提交 SDK 的业务发送须携带并复核当前代际，旧上下文不能因时间刚恢复就重新变成有效。检查与入队事务的提交、发送资格判定应有明确串行化边界；失效前已合法持久提交的批次继续保留，失效时已提交 SDK 的字节无法撤回，应按原批次追踪真实结果，不能改写或宣称没有发出。恢复后清理未持久报告缓存及首值抑制基准，再逐点接纳新有效样本；时间门槛拒绝入队不能推进报告基准。

配置接收/实际应用可以继续，但无效 UTC 期间不生成或发送带虚假时间的 config/ack、patch/ack、config/get、heartbeat 或主动 status。延迟的是应答的生成/发送，不是将配置结果无限堆在 MQTT 接收队列：按消息身份有界保存或从既有持久应用记录重建结果，恢复后根据真实提交事实和当前 activeVersion 等字段重新编码应答，不能改写原命令、重跑已提交副作用或重放已失效的旧 session 控制报文。达到缓存上限时可不应答并依靠 Hub 既有重试/重新取完整配置恢复，不能伪造 APPLIED。连接前设置的既有 connection_lost LWT 使用契约允许的 `timestamp=null`，不受授时门槛阻挡，也不能借 LWT 宣称设备在线。失效期间 Hub 最终显示心跳超时是预期行为，不能靠伪造时间续命。

- 冷启动未授时、离线保持超预算或大偏差重同步期间继续本地采集和显示，保留 Modbus/OPC UA 原有采样质量；新增的时间有效标志及本地代际只用于判断样本能否进入平台遥测。时间无效样本不进入 outbox、不冒用 RTC，也不改成恢复时刻；首版不承诺补回这段历史。
- 原生 HMI/Python 本地诊断记录暂停原因、单调持续时长和因时间无效而未上报的样本数量；未知 UTC 的缺口不伪造绝对起止时间。恢复后逐点等待在有效锚点下新完成的采样，已取得新有效样本的点可恢复上报；仍为旧代际/无效时间的缓存及 lastGoodTimestamp 不得借用新报文 Header 混入。相同数值不能让 deadband 或报告缓存跳过恢复后的首个有效样本。
- 同一 boot 断网但锚点仍可信时，可继续按原规则形成批次并进入有界 outbox；误差预算为“同步初始误差 + 已验证最大漂移率 × 同步年龄 + 修正残差”。首轮暂用 1 小时作为额外硬上限，以误差预算达到 1 秒或硬上限先到者失效。漂移率尚未实测时，一小时保持只属于待验证能力，不能宣称全程满足 1 秒精度。现场无外网不等于 PLC 与 Hub 断连。
- 已形成的 outbox 批次保持原字节、ID 和采样时间。恢复后的发送顺序为：授时及正常业务就绪检查优先；新有效数据和旧批次按有界公平预算交替发送，首轮可用 1:1，每方有待发送项时不得被另一方永久饿死；没有旧批次可发送时不空等。重试退避和原有并发上限仍生效，旧积压不得无限推迟新数据或配置/ACK。
- 旧批次只有在满足本地可信保留策略，或收到真实 Hub 的明确永久拒收时，才停止重试并记录各自原因。不能仅估算已越过 Hub 接收窗口就认定未入库：已入库但丢 ACK 的批次可能仍由既有收据去重返回 STORED。本地过期不是 Hub 拒收，也不能证明数据没有入库；两类结果分别统计，均不得伪造 STORED。队列满时保留既定有界策略并明确计数，禁止以校时为由静默清空。永久拒收、过期证据的保存也须有数量/字节上限；Python 具体规则以下文 Outbox 专节为准，原生不得借用 Python 的磁盘恢复承诺。
- 旧批次晚到必须保持历史采样语义，不能覆盖时间更晚的最新值；跨配置版本仍服从现有接收边界。错误未来时间的旧批次可能影响最新值，首版大幅回拨受限时不得强行重发来掩盖该问题。原生 PLC 当前 RAM outbox 不跨掉电持久化；Python SQLite Outbox 的承诺从成功持久提交开始，不能延伸到尚未入队或时间无效的样本，重启细则见下文。

## Python 持久化 Outbox 的时间与恢复规则

### 三类时间各自承担什么

| 时间/元数据 | 用途与首版规则 |
|---|---|
| payload 的批次及各点 `timestamp` | 原始业务 UTC；入队后不可改写，Hub 按既有契约校验与入库 |
| 可信入队 UTC、误差界及可信度 | 本地七天保留期依据，必须在成功入队事务中与批次关联；与 payload 时间不是同一概念 |
| 当前进程的单调截止时间 | STORED 等待、重试退避、限速和在途信用；只在该进程有效，不直接跨重启比较 |
| `attempts`、状态、拒收原因及历史记录 | 事务持久化；重启不清零，不改批次身份，不能把已尝试的批次重新当作从未发送 |

实现可保留旧 `created`/`next_due` 供迁移核对，但新调度不得直接依赖其系统墙钟数值，也不能把旧字段机械改成 monotonic 值后继续持久比较。时间服务应向 StoreWorker 显式传入有效性、逻辑 UTC/误差界、当前运行身份及单调时刻；存储线程实际执行时核查上下文是否已失效或过期，线程排队耗时必须推进时间或计入误差，不能把旧快照当成当前时间。授时失效时，`enqueue`、`reserve`、`acknowledge` 等任一路径都不能偷偷用 `time.time()` 执行过期清理。

新增元数据至少表达：可信入队 UTC 毫秒及误差上界、入队时间可信度（平台可信/旧库或系统时间未验证）、本地采样/任务代际、历史时间基准归属及迁移状态。名称与具体表结构在实施前定稿；这些是本地存储字段，不进入既有 DATA JSON。诊断性的入队墙钟不自动等于可信 UTC。

两种“代际”不能混用：本地采样/任务代际用于撤销缓存与旧时间上下文，进程重启、失效恢复均可改变；它不同并不自动否定已持久批次 UTC 的可比性。历史年龄按同一现场 Hub 权威及已知连续的时间基准比较，正常 Hub/Agent 重启、MQTT session 改变本身不刷新年龄，也不使其永久未知。首版限于单一配置的 Hub 时间权威；换 Hub 权威、绑定身份变化或已知大幅调时后，旧时间基准可比性须显式核验，不能仅凭 broker 地址相同或新授时成功就认定连续。新平台批次须保留用于核对的本地权威/基准归属；timeSyncV1 没有服务端 epoch 或连续性证明，无法自动证明停机期间任意调时的正确性，相关情况按首版维护限制处理。

### 重试、在途与重连

- 保留当前首次 STORED 等待 30 秒、后续重试 60 秒的策略，从实际预留并交给发送流程时以单调计时建立截止点；未能提交发送也须有界退避，不忙循环。同一进程内系统日期前跳/回拨、逻辑 UTC 平滑修正均不能提前或延后该截止点。收到可重试拒绝后，按单调时间等待 60 秒；收到 PUBACK 仅代表传输确认，不能删除批次。
- 内存中的单调截止点和在途表由进程级调度器持有，跨同进程配置重载保留，不能由每次新建 TelemetryPipeline 重置。同进程 MQTT 重连会清理旧连接的传输占用，但保留未到期的业务重试退避及累计 attempts；重连不能把所有批次立即反复发送。时间无效时截止点可自然到期，但只标记待发资格，恢复前不补发逝去的重试轮次。
- 新进程不能使用旧进程的单调截止点，也不等待旧系统墙钟 `next_due`。先重新授时和完成正常业务就绪，再将 PENDING 批次纳入当前运行调度，按原速率分批恢复发送资格；保留 attempts，原 attempts>0 的批次再次发送后使用后续 60 秒等待，原 attempts=0 的批次第一次发送仍使用 30 秒等待。当前 `reset_inflight` 的“打开/每次重连均清 next_due”语义须相应调整，不能拿它替代上述区分。
- 继续最多 8 批业务在途、最多每秒 4 批及约 512 KiB/s payload 的既有上限；按实际提交尝试计数，不因重连、失败或授时恢复绕过限速。新有效数据与历史积压按正文有界公平预算发送；恢复前从未发送的旧批次也属于历史积压，不能只用 `attempts=0` 将它误归为新数据。

预留、attempts 更新及状态持久化先事务提交，再允许 SDK 发布；提交失败不发出，提交后发送前崩溃则原批次仍可恢复，不将这类 attempts 误报为 Hub 已收到。进程级在途表和数据库状态由单一调度/存储边界协调，发送后 ACK 可能先于 PUBACK 返回，也须能定位已预留的批次并确认；不能等 PUBACK 才登记业务关联。

### 七天过期、时间未知与永久拒收

本地七天是**从可信入队时刻起的保留策略**；Hub 的七天接收边界依据既有批次 timestamp，二者须分别判断，不能用当前时间重写 payload 来延长接收窗口，也不能把升级/重启时刻当成新的入队时刻。

- 只有当前 UTC 有效、入队 UTC 可信且二者处于可比较的现场时间基准时，才执行本地年龄判断。按保守年龄下界过期：`ageLower=max(0, nowUtcLower-enqueuedUtcUpper)`，达到七天后才事务转为带本地过期来源的 EXPIRED_DATA 死信；临界值受误差影响时保留待复核。仍在本轮有效 STORED 等待期内的批次先保留确认机会，到截止点后再作本地过期转换。连续运行时可以使用同一进程单调经过时间补充年龄证据，但不得跨重启相减，也不能忽略误差界。
- 冷启动尚未授时、离线保持超预算、检测到大幅跳时或时间代际不可比较时，暂停依赖 UTC 的本地过期转换。时间未知不等于年龄为零，也不等于已过期；批次数/字节上限、拒绝新入队和死信条数上限始终生效，不能无限保留或突破容量。
- 对旧格式库中的 `created`，迁移时标记 `LEGACY_UNVERIFIED`；升级后的授时只能证明“现在”，不能证明历史入队时刻。首版不据该字段自动过期，也不改成当前时间。业务就绪后，对通过原契约、身份和哈希检查的旧批次，可按限速及公平预算发送原字节，由真实 Hub 判定接收；年龄未知数量持续可见。明显未来时间或已知回拨障碍的批次单独暂停待维护，不能强行重发。需要按历史入队年龄淘汰时，须另有可信历史证据或明确维护处置。
- Hub 明确返回永久拒绝时，保留原有错误分类并事务转死信；UNKNOWN_CONFIG_VERSION、RESOURCE_LIMIT、STORAGE_ERROR 等仍按既有契约重试。不能仅因本地怀疑超过 Hub 接收窗口就伪造拒绝/STORED。死信修剪使用稳定持久顺序（如本地入队序号）及 max_dead，累计 dead_pruned；旧墙钟不可信时也不能让修剪顺序随机变化。
- 保留当前默认 10000 条及 64 MiB payload 配额（均包含 PENDING+DEAD）、最多 128 条死信。时间未知/待维护是独立资格和诊断，不伪装为 Hub 拒收，仍纳入配额。队列满时拒绝新批次并累计 dropped，不清空未知年龄批次腾空间；统计须区分拒绝入队次数、时间无效未上报样本、过期死信和死信修剪，不把它们都宣称为已送达或每条样本丢失数。

### 迟到确认与终态竞争

真实 data/ack 的接收处理不等待 TimeValid、最新配置或新样本；必须校验授权 broker、Topic/gateway、非 retained、结构及与本地原批次的关联，并检查本地 payload 哈希完整性，不能只匹配一个任意 messageId。ACK 与本地过期、死信修剪、发送预留在同一存储串行化边界内决议。

| 本地状态与收到的事件 | 处理规则 |
|---|---|
| 曾预留发送的 PENDING 收到有效 STORED | 事务确认并删除，释放在途/调度状态；此操作不要求设备当前 UTC 有效，也不触发 UTC 过期扫描 |
| 本地保留期过期形成的 DEAD，原批次仍保留且曾发送，随后收到有效 STORED | 允许事务对账为已确认并删除；分别保留“曾本地过期”和“迟到确认”累计诊断，不继续重发，也不把它宣称为 Hub 曾拒收；这是对当前只确认 PENDING 行为的必要扩展 |
| Hub 明确永久拒收形成的 DEAD，随后出现矛盾的 STORED | 标记结果冲突供核查，不静默复活或覆盖永久拒收事实；不得继续自动发送 |
| 已 STORED 删除/死信修剪后的未知 ID，或未曾预留的记录收到 ACK | 不复活、不新建批次；按未知/迟到事件有界计数，不推断出完整已交付记录 |
| STORED 删除事务已提交后又收到重复/迟到 REJECTED | 不反向生成 DEAD 或恢复待发；原确认结果保持 |

本地过期/死信修剪是保留策略，不证明 Hub 一定没有存储。上述对账能力仅覆盖仍保有可验证关联的记录，证据被按容量修剪后不承诺无限期对账；统计必须保留这个限制。可重试 REJECTED 只更新仍为 PENDING 的重试资格，不能覆盖已经提交的 STORED。

### 进程/系统重启与确认丢失

1. 打开 `telemetry.db`，检查 gateway 身份、格式、完整性、原 payload 哈希和既有单写者锁；恢复已提交记录，未完成事务由 SQLite 恢复。未知格式/损坏应报告存储失败，不能删库重建。此阶段不依赖本机日期执行过期，也不以旧 UTC 锚点恢复 TimeValid。
2. 新进程生成新的 ProcessBootContext 和授时请求身份；尚未确认的磁盘旧批次仍保留原 messageId、bootId、sequence、configVersion、timestamp、payload 和哈希。设置重载不是新进程，不能重置 boot、遥测序号、重试调度或有效时间服务。
3. 通过当前 MQTT session 重新授时；本地采集和诊断可继续，旧批次保持在库中，暂停发送和依赖 UTC 的过期。授时失败不会清空队列；原生 RAM 队列在整机重启后的行为不能套用到 Python。
4. 时间及历史补传资格就绪后先核验可比较的可信年龄、已知回拨/未来时间障碍及原有配置接收边界，再按本节调度恢复 PENDING；不能额外等待当前期望配置 APPLIED、采集启用或新 GOOD 样本。断电经过的时长由重新取得的可信 UTC 与可信历史入队 UTC 推导，不能通过“新 uptime 减旧 uptime”计算，也不能重置七天期限。新进程的本地任务代际变化不等于历史现场时间基准已失效。
5. Hub 已提交但 STORED 丢失，或 Agent 收到 STORED 后删除事务尚未提交就崩溃时，在仍满足本地保留/发送资格的范围内允许原字节重复发送，由真实 Hub 在既有收据保留边界内去重并再次回执；不能据“曾发出/曾收到 PUBACK”直接删除。本地已过期则停止自动重发，但仍保有原记录时按前述终态表处理迟到 STORED。有效且可归属的 STORED 在恢复接收路径中不依赖当前时间；不得顺带触发依赖无效时间的过期扫描。STORED 删除事务已提交的批次不得复活；窗口外或永久拒收按真实结果处理，不能承诺无限期恰好一次。
6. 最后核对原记录数量/哈希、待发/死信/年龄未知数量、真实 Hub 收据及新样本最新值。只有已提交 Outbox 的批次属于持久恢复范围；未入队样本、损坏存储、文件系统/介质故障及超配额行为须单列，不把 WAL/FULL 配置等同于任何断电条件下绝不丢失。

### 数据库升级与旧数据兼容

实施前定稿 `telemetry.db` 新格式版本及迁移脚本/代码，并用真实结构的隔离副本测试；本方案不自动修改数据库。迁移保留全部原 payload、哈希、批次状态、attempts、拒收原因与 dropped/dead_pruned，不改配置库 `agent.db`。新增时间可信度、稳定入队顺序及其他元数据与版本号必须事务一致地提交；原 next_due 不作为新运行期截止时间，原 created 留作旧值核对，不能被覆盖来伪造年龄。

迁移前取得一致可恢复备份，遵守单写者锁，不能只复制活跃 WAL 模式的主数据库文件就宣称备份完整；迁移中断后只能回到完整旧版或完整新版。旧版本程序遇到新格式应拒绝打开，不可自动降级或初始化覆盖。降级恢复需要明确选择兼容备份及处理迁移后的新数据，不能以恢复旧库静默抹掉新入队记录。迁移、损坏、身份不符和版本不支持均须可诊断；授时协议仍保持公共 timeSyncV1，不把 SQLite 字段塞入业务 JSON。

## Hub 需要修改的内容

1. 扩展共享契约、`MessageKind`、语义校验、`HiveMqIoTTransport` 订阅列表、`IoTMessageRouter` 路由。新增公共 `IoTTimeSyncService` 或等效组件，入口接收与实际发送使用同一来源的可注入 Hub `Clock` 及独立可测试的单调计时源，不混用硬编码 `Instant.now()` 和测试 Clock，不读取数据库 `now()` 充当授时依据。落实入口双时钟记录、发送端延迟构造、跳时拒绝及处理超时规则。
2. 对已绑定、Topic 与 payload 网关一致、位于正确 broker 的请求响应；不能要求已有新鲜 heartbeat/session、APPLIED 配置或正确 Agent 系统时间。这是授时引导例外，仅放行授时，不改变业务就绪、配置发布、状态或遥测的新鲜度边界。
3. 不因收到授时请求就登记在线、激活/退休会话、更新配置版本、标记 APPLIED 或发送 STORED。重放/重复请求可返回响应或限流，但不得产生这些业务副作用；设备收到无待处理 requestId 的响应会自行拒绝。
4. 轻量、有界、限流处理；不经过完整点表快照编译或持有网关排他锁，不排在遥测事务和大量状态 UPSERT 后。绑定查询可使用有失效机制的轻量读取/缓存，不能长期缓存已解绑或换 broker 的授权。
5. broker ACL 应保证网关只能发布自己的请求，响应仅允许 Hub 发布；requestId 关联不是身份认证。首版指定单一授时响应者；多 Hub 实例共用 broker 时，其余实例不得同时响应同一网关。自动主备切换/多权威授时不属于首版承诺，替换响应者须核对同一现场时间基准及旧批次可比性，避免不同主机时钟交替授时。
6. 诊断记录请求/响应、RTT 可观测部分、处理/排队耗时和失败原因；“已发送时间响应”不等于“设备已同步”。首版由原生 HMI/Python 本地诊断报告同步结果，Hub 可由后续正常心跳和数据观察效果；如需协议级同步状态，另行定义扩展，不能给严格旧心跳任意加字段。
7. 回归正常重连与时间连续时的新会话自动恢复，以及大幅回拨被首版正确阻止的边界；核查进程启动时间、持久化会话和最新值排序，不将新 session 或服务重启视为越过历史时间边界的授权。验证旧批次不覆盖更新的最新值，保持心跳重放保护、版本及删除边界。不要为解决授时而全面放宽业务时间校验，也不为 native 增加专用判断。

## 联调与发布顺序

1. 三方先固定共同契约、参数、时间有效性与首版限制，分别确认当前工作区及运行版本；共同用有效/无效样例检查 Hub Schema、原生解析和 Python 校验结果一致。
2. Hub 先增量支持并用隔离模拟客户端验证，不要求旧 Agent 同时升级。先提供稳定的字段和引导行为，再接入真实授时客户端。
3. Python IoT 在隔离环境接入时间服务，完成临时 SQLite/旧格式副本的迁移、重试、过期、重启和故障验收；原生 PLC 按同一契约实现并编译，完成各自本地检查。两种 Agent 的完成状态分别记录，不能用一方通过代替另一方。
4. 获得届时运行操作授权后，分别进行 Python Agent 部署与 2152 原生下载/联调；两种网关使用各自独立绑定和身份，不同时冒用同一 gatewayId。验证 Hub 对两种 Agent 使用相同公共授时及业务规则，保留旧 Agent 共存验证。

新 Agent 面对尚未支持授时的旧 Hub 应有界退出首轮并显示“授时超时/Hub 未响应”，首版不能仅凭超时区分不支持与网络故障；不能卡死采集，也不能无提示把错误系统时间当可信 UTC。用户可明确选择系统时间源，但要说明该选择不保证系统时钟准确，也不自动赋予旧 Outbox 历史时间可信度。以下均为后续实施验收要求，本次完善文档不授权修改代码、下载程序、调整时钟、迁移数据库或操作运行设备。

必测：

- 在隔离测试条件下，设备日期错误/偏差数小时仍能先通过 MQTT 获得时间，再建立心跳、配置及真实入库；故意破坏系统日期会影响其他服务，须在维护窗口测试，不应直接改正在运行设备的 RTC。
- 断网、broker 重启、Hub 重启、PLC 整机重启，以及 Python 进程/宿主机重启后的正常自动恢复；Hub 入口繁忙或数据库锁等待时授时仍有界响应。
- QoS 重复、retained、乱序、旧 boot/session、过期 requestId、错误网关、超大负载、过高 RTT、负处理时间以及 Hub 时间跳变。
- 运行中时间不倒退；旧 outbox 批次不改 ID/内容；没有因同步失败伪造采样时间、GOOD 状态、APPLIED 或 STORED。
- 授时期间分别注入 Hub 向前/向后跳时，超过 50 ms 双时钟差异时不发响应；发送执行器积压不能使用排队前的 `t3`，超处理预算或 RTT 的样本被拒绝。覆盖 PLC 有符号差值、负延迟容差及单调计数长周期边界。
