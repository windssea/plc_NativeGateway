# 三方联调主线与 P06 验收复审（2026-10-26）

> 2026-10-26后续文档已按本复审整理为[JOINT-PLAN/1](三方联调实施与统一验收-20261026.md)及[MCP-JOINT-GAPS/1](../../PLCnext-Engineer-mcp/docs/三方联调MCP修复清单-20261026.md)。本文保留复审时观察；实施/统一验收顺序以新计划为准，P06暂停，原指标未变。

本轮依据用户要求停止继续滚动 PLC 性能测试，重新审视指标、时间依赖和三方计划。本文是复审结论及后续实施建议，不修改 HUB-IOT-PLC-P0/2、既有 resource-profile 或任何 PASS/FAIL 门槛，不把旧 P06 失败改为通过。本轮没有修改业务代码、切换服务、创建数据库、下载或控制设备，也没有使用 Computer Use。

## 1. 主线和进度判断

主线仍为 Hub、Python IoT、原生 PLC 按同一时间接口、reportPolicyV1、不可变 DATA/ACK、缺口计数和恢复规则对接。三方应统一可观察语义和同负载验收，不要求 SQLite 与 RAM 的介质能力、内部结构、CPU 参数相同。

目前仍停留于阶段 1 的 PLC P06 性能分项，尚未进入完整公共 MQTT 授时和整体验收。反复微调单个 PLC 候选，超过了这一分项对三方联调主线应占的比重；这属于实施优先级偏移。Hub H01～H05、IoT I01～I06 已有各自开发/分项证据，不能因此推断两种 Agent 的完整同场景联调已通过。P06 未放行应保留，同时可继续推进不依赖 P06 成功的共同功能、时间前置和隔离对标工作，不总括宣布阶段 1 完成。

无独立共同可信时基的现场，原计划已经要求将阶段 2 的最小授时和必要存储保护提前。先打通这一前置属于既定依赖修正，不是跳过阶段 1 所有权或性能验收。

## 2. 指标合理性及排空口径

50 台/250 点、5 秒周期对应输入 λ=50 条/秒；300 秒无确认形成约 15000 条。稳定恢复必须 μ>λ，但这只是能最终追平的必要条件，不能证明规定时限内恢复。

90 条/秒可以作为恢复余量目标，不能称为设备天然上限。若将 540 秒明确为“恢复后持续采样、总积压回到正常基线”的期限：

- 立即恢复确认时，需要 μ≥50+15000/540≈77.78 条/秒。
- 前 60 秒仍完全没有确认且持续新增，60 秒时积压约 18000 条，剩余 480 秒，需要 μ≥50+18000/480=87.5 条/秒。因此 90 有合理的保守工程依据。

这是对候选业务定义的推导，不是认定旧计划已经按这一含义验收。实际须纳入初始占用、质量突发、部分确认、重试、到达突发及净服务波动，不能仅套平均公式。

现有 `summarize_phase1_performance.py` 的 historyClearBracket 检查历史类别 FIFO 和该类别批次是否为空。它不是全 OwnedCount 回到正常水位。boot52 恢复后历史清空区间472.94～483.06秒、当时持续采集，但首个历史类别为空的观察中 Captured=43000、Stored=34832、Owned=8168。该证据只证明恢复前历史类别清空，不能证明全部积压或新数据延迟恢复。这解释了历史540秒子项通过而总释放63.158条/秒的表面矛盾，不推翻该轮原始完整性证据。

需在下一次联调前明确三个独立结果：故障窗口 cohort 全部 STORED/本地释放的期限、全局积压回到正常基线的期限、新数据采集至入库延迟及最大年龄。用独立事件/收据关联验证，不以 QueueHead[1]=0 或最终暂停排空代替。

1ms 是主任务保护预算；最初缓冲方案称其为初始目标，阶段0已将其固定为硬门槛，不能因当前约1.23～1.25ms而直接改成通过。20ms周期内，1ms相当于5%的时间额度；当前825μs调度量相当于每秒41.25ms，只是该流水线的可用量，不是2152全部计算能力。需要补齐同负载原工程的控制任务期限、抖动及资源余量依据，决定继续把1ms作为受支持硬约束，还是正式评审新的独立遥测任务/预算 profile。单纯放宽为2ms或看到整任务暂未超20ms，都不能直接放行。

## 3. 为什么慢，与时间同步有什么关系

| 证据 | 能支持的结论 | 不能支持的结论 |
|---|---|---|
| 64条真实满批的组包非摘要约11ms，三次SHA合计约17～20ms累计调用时间 | ST JSON/复制及三次整包计算消耗了大部分每秒调度量 | 不能用累计调用时间充当同一扫描峰值 |
| 15244字节无I/O独立825μs夹具，组包非摘要10.931ms、三次SHA20.425ms | 此长报文90条/秒仅上述成本约44.1ms/秒，已超过41.25ms/秒调度量 | 不能据此认定所有较短报文都无法达到90 |
| 两层轮流优先开关同相，修正后boot59饱和释放70.513条/秒 | 存在实际调度偏置，值得保留明确所有权下的公平调度 | 不能把不同故障窗口和探针负载的全部增益归因于一个改动 |
| 宽预算1800μs诊断达到137.541条/秒，但新增峰值2133μs | 当前架构在更大额度下能超过90，原预算/流水线服务量是重要限制 | 不是1ms验收通过，也不是2152在所有并发下的性能保证 |
| Hub事务均值448.681→304.819ms，PLC吞吐未随之稳定增加 | Hub确认长尾值得治理，但并非剩余唯一主瓶颈 | 不能据此认定继续增加MQTT并发即可解决 |

源码的预算计时使用 GET_MICROSECONDS，运行期重试/调度使用 TON 推进的 NowMs；UTC 当前由 NG_Unix(RTC, UtcOffsetMinutes) 每周期换算。两端公共 MQTT 授时尚未实现，Python CaptureTime 也明确为 SYSTEM_RTC_COMPAT。无网络夹具仍有SHA/组包成本，因此现有证据不支持把吞吐不足归咎于MQTT校时。

时间仍是另一条真实风险：RTC前跳/回拨可能造成控制新鲜度拒收、采样时间失效和历史年龄错误；Python Outbox `_expire(now)` 仍有兼容墙钟七天比较，单调重试已改并不意味着持久过期安全已改。PLC每扫描RTC换算也有计算成本，但尚未单独取证，不能将其称为主要瓶颈。预算墙钟耗时还可能包含抢占，未区分前不能全部解释成纯CPU指令成本。

## 4. 优化方向及测试止损

1. 先统一三方端到端验收语义，保留真实STORED、原字节重试、同点同UTC多事件和有限所有权，不为性能删除正确性保护。
2. 优先评审三次SHA的必要边界：冻结时摘要、发送前完整性、ACK前所有权校验各防什么错误。可评估在不可变单写者和槽代际成立时复用已验证结果，或核实可用原生实现；不能直接删掉两次摘要，须先说明内存损坏检测、重试和迟到ACK保证如何保留。Hub独立哈希去重和提交后STORED继续保留。
3. 组包沿用有界批次，继续审查增长字符串的重复复制和重复格式化，能以同字节、代际有效缓存减少的工作优先减少。维持64上限，不靠扩大批长或增加并发掩盖成本。
4. 已有批次流水线应使组包、待发送、在途等待、ACK验证/释放能够有界重叠；按测得服务成本分配预算并防止ACK饥饿。先检查初始化、最终提交和全批引用释放等不可抢占步骤的最坏耗时，避免仅在循环入口检查截止时间。
5. 如果1ms必须保持且计算模型明显不够，评审低优先级遥测任务与双缓冲/所有权交接，而非反复调整同一循环。当前MCP只支持修改既有单周期任务，不支持新建/删除任务；该方向需要工具能力扩展和正式设计，不能本轮直接套用。
6. 每次物理验证前写清单一假设、预测改善量、取证点、失败后的去向；同一方向一次有效对照无收益即停止该方向。当前先不继续上传v37/v33或重复5分钟故障，待验收定义与算法方案评审后再选一个有依据的候选。
