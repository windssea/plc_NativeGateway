## 实现与三方契约

`NG_Diagnostics` 每秒在同一 IEC 扫描内生成带奇偶修订号的快照：共同顺序的 16 项 Total、入口待决定、全部未终止事件、隔离/不确定保留量、批次数、RAM 配额、最老年龄及最近缺口。HMI ResourceStatus 使用同一快照摘要；legacy heartbeat.queue 的结构和含义不变。终态释放及 tombstone 清理同步更新保留 gauge，累计损失不冒充当前保留量。

RAM 启动仍报告 VOLATILE_RESTART/UNCERTAIN、eventCount=null，accountingComplete=false 在本 boot 内保持；已知 Total 是事实下界。两轮从 sampleSeq=1 开始的完整 cohort 可以独立对清，不能据此把前一 RAM 运行期损失改成 0。无年龄或未知重启缺口的身份/配置/时间导出 null，不用零伪装已知。

当前时间路径仍是 `SYSTEM_RTC_COMPAT_UNVERIFIED`。未实现 MQTT timeSyncV1、可信 Hub UTC 或新诊断 Topic 发布；原生内部 Reason/Outcome 数字不能直接作为公共枚举发出。Hub 与 Python 入口文档、共同资源 profile 已同步本轮状态，冻结 P0/2 和协议/topics 文件未变；本轮没有修改 Hub/Python 业务代码。

`NG_AuditCapture` 在入口冻结时复制原事件；`NG_AuditDecision` 记录过滤/接纳/已知未发/资格未知结果。512 条审计环独立持有配置引用，32 条关联环保留冻结 messageId、SHA-256、代际及最多 64 个 sampleSeq，其数组位置就是 valueOrdinal。业务槽释放不影响审计副本。满环覆盖增加 AuditDropped/AssociationDropped 并令 EvidenceComplete=false，不冒充业务丢样、不阻塞采集。四个配置槽和这些审计引用的切换压力仍须在后续验收覆盖。

外部导出器已由逐点 RPC 调整为有界批读：每轮最多 64 个入口事件/16 个关联，每个 RPC 至多 64 字段；缓存配置元信息和点位规则，避免每个事件重复大字典。每次成功 flush/fsync 后才写 boot 绑定的审计 Uint64 游标；不伪造业务 ACK、不改变业务所有权。SDK 游标编码修复为显式 `RscVariant(value, RscType.Uint64)`，并有主机回归覆盖。文件独占、最多 64 MiB/100000 条；旧 boot、覆盖、配置变化、磁盘失败、连接中断或容量满均不能静默续接为完整证据。`--wait-ready` 最多 300 秒，`--after-boot` 只在尚未进入候选时等待新 boot。

`NG_DeliveryParallel` 分离 ACK 与发送前摘要状态，先推进 ACK，避免取消未完成的发送校验。`NG_Add4` 用 LWORD 掩码保持 DWORD 模 2^32 语义；`NG_StringSHA256` 内联轮函数求和，仍每扫描最多处理 8 个 SHA 块。41 项回归和长报文摘要通过，但实测吞吐仍不达标，不能将代码优化等同于性能放行。源码打包器、故障控制、记录器和复核工具见[测试说明](../tests/README.md)。

## 两轮真实 Hub 闭环与故障边界

完整链路为：独立入口副本 → 基于冻结配置的独立 reportPolicy oracle → 冻结 sampleSeq/messageId/valueOrdinal → 原字节 SHA-256/重试不变 → 真实 STORED → 暂停后本地 Owned/Ingress=0 → 现有开发库逐收据哈希及样本多重集核对。两轮共 83500 条、1311 批，业务丢失/拒绝及审计/关联覆盖均为 0。每轮 GapRecordsTotal=1 表示未知 RAM 重启缺口，不是已知丢了 1 条样本。原始 JSONL、wire 与展开映射留本机；[证据清单](../tests/validation/p05-p06/evidence-manifest.json)保留文件大小和哈希，紧凑结果可进入 Git。

boot32：验证变体仅关闭候选 DATA 发送门约 300.813 秒，采集继续，恢复时 Owned=15000；随后真实确认并排空。该注入覆盖本地发送暂停，不是物理断网，也没有停止共享 broker/后端。恢复窗口两快照 `(NowMs, Stored)` 为 `(619520,15558)` 与 `(982000,36422)`，即 `(36422-15558)/362.48 = 57.559/s`。历史队列观测从恢复后约 514 秒仍有积压，到约 555 秒已清；该观测区间跨过 540 秒门槛，**不判定在 540 秒内清空通过**。最终 55250 条全部释放，68038 个受测扫描最大 13.833 ms、超 20 ms 为 0；这仍不是纯正常负载 30 分钟证据。

boot33：仅禁止候选应用真实 ACK 约 300.937 秒。Hub 正常提交/回复，候选重试原字节；恢复时 Owned=15250。最终暂停、排空 28250 条，全部真实 STORED/本地释放及数据库闭环成立。36713 个受测扫描最大 23.515 ms、超周期 1 次；统计包含 StartupReady 后的早期通信/质量事件，未分离根因，不能称稳态零超期。暂停后排空是维护清理，不冒充持续 50/s 下 540 秒恢复验收。

每轮原生取证均在完整 boot 起点前布置，记录器结束及本地游标追平后才更换程序。为取得新 boot 使用 IEC 运行时 `IPlcManagerService.Stop(False)` 后 `Start(Cold,False)`；曾尝试 service2.Restart 但 boot 未变，记录为无效尝试。未重启 OS、改设备时钟或实现 RAM 持久化；两次受控重启在旧队列排空后进行，不能证明带待处理 RAM 记录重启无损。

早期失败证据保留：boot29 逐点导出过慢导致审计覆盖；boot30 游标 int 编码失败；boot31 的启动等待 120 秒超时。相应业务分别 6250、8250、7500 条排空后才继续；这些窗口没有完整审计，不纳入通过 cohort。窗口控制失败及用户多次误按 Escape 是执行历史，恢复后继续；每次中断后先解除故障开关、暂停并排空，最后再恢复原工程，未将失败记录删成全程成功。
