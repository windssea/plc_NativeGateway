**判断：尚无证据表明 2152 天生不能带 50 台/250 点，也没有厂商给出本方案 JSON、摘要、所有权、MQTT STORED 全链路的理论 90 条/秒保证。当前只能判定该实现尚未在约定预算下通过。** PROFINET 的 64 设备限制不适用于本工程的自定义 Modbus TCP 客户端。

负载应拆开计算：250 点/5 秒是约 50 个物理结果/秒，不是每秒 250 次或每 20 ms 同时读完 50 台；按当前每点独立读最多约 50 个请求/秒。连接数、正在等待的请求数、结果速率和业务确认释放速率是四个不同指标。本方案 1 ms 新增工作/20 ms 周期相当于只给新增路径平均约单核 5% 的周期预算，瞬时初始化还必须单独满足峰值。它比“CPU 能否完成 20 ms 整个任务”严格得多。

按冻结目标做容量推导（非厂商承诺）：输入 50/s，中断 300 秒约积压 15000 条；若恢复释放 90/s，净排空 40/s，理想历史排空约 375 秒；若只释放 60/s，净排空 10/s，约需 1500 秒，超过当前 540 秒目标。若要求 540 秒排清，理想最低持续释放为 50+15000/540≈77.78/s，90/s 是带余量的目标。该推导忽略调度与协议开销，不能代替实测。

下一步应在恢复的 GOOD 来源、250 点稳定 5 秒网格、MissedPollCycles=0 前提下重新测固定负载，分别记录每核/任务、来源、JSON、三次完整摘要、SDK 等待与 Hub ACK 延迟；必要时独立做更宽工作预算的诊断对照，明确排除于 1 ms 验收。若更宽预算可达 90/s，则优先评估通信工作任务分离或实现优化；若仍达不到且核负载/计算单元饱和，再评估 C++/IoT 分工或更高性能控制器。跨任务方案需要新的所有权/并发设计，当前没有直接启用或改变验收标准。
