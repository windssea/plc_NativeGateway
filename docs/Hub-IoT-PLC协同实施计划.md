## 两份方案的关系与优先级

Python I01/I02 已提交（IoT `c233bb8`、Engineer `f287091`、Hub `1e69ebb`）；[I03/I04](../../PLCnext-iot/doc/verification/2026-10-24-i03-i04.md)随后提交为 IoT `621e827`、Engineer `e6215b0`、Hub `0efeae8`。最新 [I05/I06 验证](../../PLCnext-iot/doc/verification/2026-10-24-i05-i06.md)完成本地 16 项 Total/逻辑快照/有界记录器，并在原有开发 SQLite、现有 Hub/开发 PostgreSQL 验证真实 STORED、软件退出恢复、去重/删除及实际 SQL 故障回滚；152 项隔离测试通过。没有创建临时数据库或启动运行 Agent/设备，后端保持唯一。SQLite 表格式未变，跨进程采样关联继续明确未知；平台时间迁移、物理断电、确认吞吐/排空和三方整体验收不能据此总括放行。

授时解决“采样发生在什么时候”；采样缓冲解决“应上报事件在交付前是否被覆盖或淘汰”。SQLite Outbox 只能保护已经成功入队的批次，不能反推之前每次采样都被保存；Hub 全部 STORED 也不能证明设备从未组包的样本没有缺失。因此两种 Agent 都需要覆盖从采集入口到真实入库的完整边界。

推荐先固定三方规则与时间接口，再修复采样进入 Outbox 前的缺口，随后完成公共 MQTT 授时，最后扩展原生文件日志。这个顺序以当前联调已有可核验的局域网共同时间基准为前提：原生 PLC 的时间路径已实测，而满队列后的周期历史缺口已有实际证据，优先处理该缺口更直接。当前时基在隔离验收中仍需核实，不能仅凭系统日期看似正常就标为平台授时可信。

若目标现场只有 MQTT、没有可用的局域网时间服务且设备日期不可信，则必须先完成最小 MQTT 授时引导和采样时间有效性，再开放带 UTC 的遥测及补传；不能机械套用“缓冲先行”。原生文件日志跨重启的年龄重建依赖可信时间恢复，应放在授时规则及 RAM 缓冲稳定之后。

## 三方职责与差异

| 参与方 | 必须承担的工作 | 不应重复承担的工作 |
|---|---|---|
| Hub / PLCnext-Hub-Backend | 时间权威、公共契约、历史版本/身份校验、原字节去重、批次事务提交后才 STORED、最新值不被旧数据回退；消费共同诊断并展示缺口 | 不用 Hub 接收时间覆盖采样时间，不把收到批次等同于设备周期历史完整，不为某一种 Agent 增加特判 |
| Python IoT / PLCnext-iot | 检查采样事件到报告选择再到 SQLite Outbox 的每个有界入口；时间服务、持久化重试/过期/重启恢复、真实缺口及拒绝入队计数 | 不另造一套与公共 timeSyncV1 不同的授时协议；已有 Outbox 不推倒重写 |
| 原生 PLC / PLCnext-Engineer | 分离最新值与历史事件，交付有预算的 RAM 采样 FIFO、不可变批次、死信/迟到 ACK 及缺口诊断；接入公共时间服务；后续可选文件日志 | 不把 RAM 可恢复补传说成掉电持久化，不照搬 Python 的 SQLite 或内存容量参数 |

总体语义一致，存储能力与满载策略允许不同：原生候选为淘汰最旧数据以保持新采集，Python 当前为满额拒绝新批次并保留已有记录。两方都必须明确策略、容量、损失单位和诊断，不能用统一名称掩盖不同的数据保留结果。

## 共同的数据生命周期

1. **采集完成**：成功或最终失败都形成可关联事件，保留原值、质量、原采样时间和单调时刻；内部重试不是新采样，不能靠改时间制造新值。
2. **上报资格选择**：按 reportPolicyV1 的 reportMode、调度网格、deadband 及质量变化在入口决定应上报事件；不能默认每个原始采样都必须上报。符合规则的有意过滤不计为缓冲丢失，batchInterval 只管物化，已经选中并接纳的事件不能再被无声覆盖。
3. **本地接纳**：进入有界采样暂存/FIFO。区分尚在 RAM 的接纳和已完成持久提交；容量满、入口失败、版本切换及时间无效均给出准确结果，未接纳不能推进报告基准。
4. **批次冻结/所有权转移**：完整 payload、messageId、bootId、sequence、历史配置映射确定后，不再改变原字节或将同一采样重复算成两份待处理数据。Python 的持久可靠边界是 SQLite 入队事务提交；原生 RAM 模式没有这个持久边界，文件模式以定义的日志提交点为准。
5. **传输及确认**：MQTT PUBACK 不等于交付，只有真实 STORED 才证明对应批次已提交。旧数据与新数据在限速预算内公平发送，控制/授时/业务 ACK 优先，不能等待全站历史排空才更新在线状态。
6. **终止与对账**：STORED、明确拒收、本地过期/容量淘汰以及交付不确定分别记账。迟到 STORED 只处理可核验的原记录或有限 tombstone，不误删复用槽；本地淘汰不能断言 Hub 未入库。

相同点位可能出现相同 UTC 时间或相同数值，不能只用点位+timestamp 唯一识别采样。验收使用内部采样身份及“采样—批次—原始哈希—Hub 收据”关联，关联信息可由有界本地诊断与外部验收记录器保存，不直接向严格 v1 DATA 添加未知字段。

## Python IoT 需要补齐的采样缓冲范围

当前 `points/samples.py` 的 SampleBuffer 容量默认 1024，满时删除最旧样本并增加 dropped；`reporting/engine.py` 的 latest 按点位保留最新值，报告窗口允许合并；Outbox 满时拒绝新批次。这些是不同边界，不能将其损失都归入 outbox.dropped，更不能把 latest 合并全部定义为缺陷。

reportPolicyV1 已固定选择时点、质量/FIRST、名义周期及 pending/committed 基准；当前 latest 合并只列为旧行为。实施时据此审计：报告线程/SQLite 变慢、输入队列溢出、时间失效、配置变化、批次拒绝入队及正常退出 flush。对已经被选为应上报的事件，使用独立有界队列或等效机制保存其不可变内容与配置身份；HMI 最新值继续独立更新，不能再从后来覆盖的 latest 重建历史。

至少区分 sample_dropped（入口溢出）、按策略有意合并、时间无效未上报、版本切换丢弃、Outbox 拒绝入队次数、已物化批次淘汰及交付不确定。涉及样本数时须有实际事件关联，不能把一次入队失败直接换算成所有中间采样已知丢失。Python 的容量、CPU/内存及存储预算单独测算，不套用 PLC 的 4 MiB、32768 条或五分钟结论。

## 共同时间与恢复要求

时间来源、引导顺序、失效矩阵及大幅回拨限制以[MQTT 平台授时方案](MQTT平台授时方案.md)为准。缓冲记录须具备采样时间有效性、用于撤销旧缓存的本地任务代际及历史时间基准归属，不能只保存一个裸 UTC 数值。

没有可信时间时，继续采集和本地诊断，不把无效时间样本送入平台遥测；同进程短时断网可在保持预算内继续形成有界记录。时间失效不停止入站配置/真实 ACK，历史批次原字节保留。新连接先复校并恢复正常控制提交，历史补传不等待新 GOOD 样本、采集启用或期望版本 APPLIED；显式维护停发、身份/版本/删除边界仍适用。

首次正常控制用 CONTROL_SEND 判定，复校通过即可提交，不等待“控制已提交”；DATA/新诊断的 SEND 才等待本 session 正常心跳及 config/get 均成功提交 SDK。时间失效只清无效缓存/任务，不清已接纳 FIFO：其历史所有权、原 UTC/配置保持，恢复后使用新任务令牌物化；确需终止必须精确记账。

Python 的七天本地保留期、PLC RAM 模式的 900 秒候选年龄以及文件模式的 3600 秒候选年龄属于各自本地策略，均不同于 Hub 的批次接收窗口。判断本地过期须有可信依据；不能用“疑似超出 Hub 窗口”替代真实结果。原生运行期年龄用单调计时，跨重启恢复用可比较的可信 UTC；Python 规则详见授时文档 Outbox 专节。当前原生 RAM 数据不跨整机重启，不能因 Python 恢复通过就宣称原生也通过。

原生采样 FIFO 中尚未冻结的历史样本允许在恢复后组新消息，但原采样时间/配置身份不变，冻结后再重试必须保持原字节。已冻结 Python 批次与原生 PREPARE 批次不得为更新外层 timestamp 而重写；两类数据不能混用恢复策略。

阶段 1 的 Python/PLC 工作可以在共同规则固定后各自实施，不要求两个实现同时切换上线。阶段 2 内部仍是 Hub 支持先行，再分别接入两类 Agent。对新现场“最小授时先行”不意味着必须先完成全部 SQLite 迁移或完整文件日志，但必须先覆盖首次可信 UTC、业务门槛和所有存储入口的无效时间保护；必要元数据无法安全表达时，其最小显式迁移同步前移，不能以阶段划分保留会误删历史的旧过期路径。

## 共同诊断与验收

缓冲方案中的 `diagnostics/buffer` 应作为两种 Agent 共用的版本化扩展，而不是原生专用通道。三方先固定最小公共字段、计数单位、能力差异和未知年龄表达，再由 Hub 消费展示；RAM/SQLite/文件模式的附加字段通过明确能力/版本表达，不改变既有 heartbeat.queue 含义。旧 Hub 不支持时保留本地诊断，不能宣称远程缺口已告警。

验收同时覆盖：正常报告策略与有意合并；五分钟通信/Hub 故障；输入队列或 Outbox 满；配置增删/停用/期望版本未应用；逆序/重复/迟到 ACK；时间失效和恢复；Hub/Agent 独立重启；Python SQLite 与原生日志各自提交点崩溃。原生文件日志的物理断电另验，未参与的模式不能借用另一模式的结论。

对采集入口中按策略应上报的事件做互斥集合核对：已证实入库、仍待处理、已知未发送损失、明确拒绝/隔离、交付不确定。外部验收已证实保存的事件优先归为入库，不再重复计入待处理或不确定。队列归零、250 GOOD、批次序号连续和 droppedBatches=0 都不足以单独证明采样历史完整。

本文与JOINT-PLAN/1统一当前优先级与职责；共同接口/语义以阶段 0 定稿为准，授时状态/存储恢复与原生容量/任务细节分别参考两份方案。发现冲突应先修订共同规范版本和黄金样例，再同步三方实现，不由某个项目临时放宽时间或交付边界解决。
